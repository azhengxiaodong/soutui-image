## 维护与发布

业务程序仍为Python。规则数据在 `src/soutui_image/resources/review_rules.json`。原版规则已逐字核对35份实际图像记录、49个已完成整图阶段，文字、模型及流程未改变。

修改规则时：新建不同版本，保持对应引擎兼容；在本机完成实际正反图片及未参与调参样本的质量对照，登记与规则内容SHA-256绑定的验收证据。只有验证通过后才执行发布，不把调试草稿推给客户端。单纯编辑文件不等于发布。

维护入口：

```powershell
# 仅首次创建私有仓库和本机签名配置；已有仓库会确认私有状态
python run_updates.py init-private

# 发布规则。证据中必须有status=verified与对应bundle_sha256；序号递增
python run_updates.py publish-rules --rules 新规则.json --evidence 验收证据.json --tag rules-新版本 --sequence 新序号

# 维护机可独立检查实际发布，不触发生图和审图
python run_updates.py check --maintainer --data-dir data

# 程序在独立验证与打包通过后发布；沿用上一稳定规则资产
python run_updates.py publish-program --program release/搜推生图-Windows测试版.zip --evidence 对应package_release/release.json --tag app-新版本 --sequence 新序号 --program-version 新版本
```

发布端使用当前电脑Git凭据管理器中正常登录的GitHub账号；签名私钥在 `data/local/update_signing_key.dpapi`，由当前Windows用户加密保护。公钥和固定仓库信息位于程序资源中。签名私钥不上传、不分发；每台客户端只需本机只读授权。原始私钥文件不能跨用户/电脑直接解密。

## 任务与规则版本

每个商品首次处理时创建 `data/tasks/product_商品ID_rules.json`，绑定当前白底图SHA-256、规则SHA-256和版本。已有生成历史但没有新绑定记录的商品沿用原规则，不因自动下载而换版。线程显式继承商品规则，九组与全部补生共用同版。

需要把已存在商品升级到新规则时，使用明确操作：

```powershell
python run_pipeline.py --input 白底图目录 --data-dir data --product-id 商品ID --recheck-saved --upgrade-rules
```

该操作会把旧通过按新规则重新核对，可能向Codex重新提交对应图片并消耗账号额度。它不新增网站生图，保留旧输出副本和原轮次；这不属于启动时自动更新的动作。每次在操作前明确复核范围。

## 客户端首次授权

在GitHub Settings → Developer settings → Personal access tokens → Fine-grained tokens，为目标电脑单独生成令牌，仅授予这个仓库的Contents读取权限。也可由具备仓库权限的使用者自行生成。将令牌直接填写到目标软件的“只读授权”，不需要在聊天中传递。

首次验证成功后，令牌保存在该电脑运行记录的 `local/github_updates.dpapi`，不能作为通用授权文件复制到其他电脑。每台电脑仍需自己的Codex登录和生图网站登录。

首次把0.2.1完整ZIP交给目标电脑，解压并配置一次只读授权。后续日常规则更新在维护机验证、签名发布，目标软件启动或点击“检查规则更新”即可获取。功能需要升级时，在任务暂停或结束后点击“程序升级”，无需维护者逐台重新发送ZIP。令牌到期或撤销需要重新授权；网络应能访问GitHub API与Release下载地址。

## 校验与回退

客户端验证私有仓库身份、维护端签名、完整内容SHA-256与引擎兼容范围，正常失败保留旧指针。已有任务不被中途换版；未完成任务不复用不同规则的通过缓存。程序升级在空闲时由独立副本替换目录，旧程序保留备份，运行记录不清空。

传输测试预发布 `transport-validation-20261029` 只改版本元数据，不改提示词，不进入默认稳定通道，也不是新的视觉准确率验证。跨电脑实际首次授权与完整业务验收仍需在目标电脑执行。
