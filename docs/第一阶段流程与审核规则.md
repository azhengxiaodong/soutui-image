# 第一阶段流程与图片审核规则

本文件根据用户逐步提供的截图和说明整理。流程和参数已确认；标有“建议”或“待明确”的内容尚未确定。当前正在按板块独立开发与验证，实际完成状态见模块验收记录。

## 2026-11-03 最新审核口径与重测

用户最新确认：图一、图二程度的细微袖口边缘起伏/小齿/细窄小孔或网眼纹理不影响使用，可以保存；明显加宽的独立大花边带、大面积镂空、成层荷叶边、翻边、束口等实际改款仍不合格。细窄领口、裤脚边饰同样不要求微观纹理完全一致。不可仅因放大后的细小起伏拒绝或待复核。

整体左右镜像仍允许；核对口袋所在前襟、扣子固定衣片、扣眼/自由边的叠合关系，只有部分结构接反、错位时必须拒绝。图三是本轮人工确认的明显结构错误负例，不能分别镜像不同部件来解释。

用户进一步确认：姿势、屈腿、遮挡或画面裁切造成脚踝不可定位，但没有明显改短证据时，不单独待复核，可以按可见范围通过；不得编造已核验及踝。明显七分裤、短裤或明确较长裸露小腿仍拒绝，其他可见结构模糊仍待复核。此条取代下文历史上仅脚踝定位不足也待复核的标准。

提速保留Sol、账号当前推理设置、原始图片、两次独立整图审核和扣位专项；通过最后两项并行和复用身份/哈希核验的定位断点减少重复等待。未完成或失败检查不作为通过。

用户明确结束原批次并清空本地任务、审核和输出，保留原图和账号配置，下一批从零测试。日后正常续跑仍不得静默清零轮次。本节优先于下文历史更严格的“袖口一点起伏也拒绝”口径。实测范围见本轮验收，不保证所有商品零误判。

## 一、输入与项目对应关系

- 生图网站：https://ai.51dingxiao.com/app/
- 输入是用户指定文件夹中的商品白底图片，以当前图片对应的商品 ID 关联后续任务。
- 每张商品白底图分别新建一个项目。
- 每个项目使用同一张白底图建立 9 行服装任务。
- 9 行分别使用 9 个不同的收藏参考图分组。
- 用户已确认每个分组有 5 张参考图，每张参考图生成 1 张结果；每个商品的目标结果数量为 9 × 5 = 45 张。
- 对文件夹中的其他商品分别重复完整流程。

## 二、创建项目与上传服装

1. 首页点击“我有参考图”。
2. 点击左侧“批量出图”。
3. 点击“新建项目”。
4. 选择“模特换衣”，点击“确定”。
5. 上传当前商品 ID 对应的白底图。
6. 根据当前白底图的实际内容选择服装类型。

| 图片内容 | 网站服装类型 |
| --- | --- |
| 上衣与裤子的两件套 | 套装 |
| 单件上衣 | 上装 |
| 单件裤子 | 下装 |

7. 点击“确认”，进入项目明细。
8. 项目此时已有 1 行，通过“添加服装”继续添加同一张图片，补充 8 份，最终编号为 1～9。

不能将整个输入文件夹中的不同商品混成这个项目的 9 行。其他服装类型的选择规则尚未说明。

## 三、选择收藏参考图

1. 逐行点击“参考图”，再点击“我的收藏”。
2. 用户目前有 17 个模特参考图分组，不将“未分组”作为候选。
3. 在每个项目中随机选择 9 个不同分组，分别分配到 9 行；不重复的范围是当前项目。
4. 分组栏可横向滚动。
5. 进入选定分组，点击“全选”，再点击“使用选中参考图”，将组内参考图应用到当前行。
6. 9 行全部配置好后，点击右下角“批量生成”。

每行使用整组 5 张参考图。当前业务规格已明确为 9 组、每组 5 张，共 45 张参考图；实际页面与此不符时需识别数量异常，不能静默漏选。

## 四、固定生图参数

| 参数 | 已确认的设置 |
| --- | --- |
| 图像比例 | 3:4 |
| 清晰度 | 2K |
| 生成时间 | 立即生成 |
| 模式 | 均衡 |
| 数量 | 每张参考图生成 1 张 |

设置后点击“开始生成”。每个商品预计生成 45 张结果；实际成功数量还受生成失败影响。尚在生成或生成失败的项需要单独跟踪。

## 五、查看生成状态

1. 提交后，批量项目列表会显示“生成中”。
2. 点击左侧“模特换衣”，在右侧查看生成记录。
3. 每行所用的参考图分组对应一个结果板块，当前商品的 9 行对应 9 个板块。
4. 显示“生成中 x/y”的板块还在处理。
5. 出现“下载全部”的板块按用户流程进入可下载状态。
6. 同一板块可能同时显示“下载全部”和“1 张失败（已退积分）”，需要记录部分失败，不能据此认定全部图片成功。

建议实现时保存商品 ID、项目标识、行号、参考分组和结果任务标识的对应关系，避免将历史结果或其他商品的结果混入当前商品。技术性生成失败的补救流程仍待用户说明。

## 六、逐张审核服装一致性

### 质量优先的提速约束（2026-10-29 用户确认）

- 用户人工审图约每张5秒，这是人工速度参照，不是已经验证的AI速度目标；不承诺Codex达到同等速度。
- 日常目标仍是自动生成、每张审核、按原组限次补生和保存，不把长期逐张人工筛选作为默认流程。
- 正确率优先于速度。优化同时评估错误图片被放行（漏判）和正常图片被拒绝（误杀），不得只用整体通过率、模型自评分或耗时证明正确率。
- 优先减少无效等待、优化并行调度、复用身份及哈希匹配的已完成结果。不得将原图特征缓存当作不再查看真实原图的理由。
- 减少审核轮次、合并专项、降低推理设置、换模型或压缩图片细节均属于待验证实验，不能因预期更快就直接进入正式版。当前正式审核链路、模型和设置不因这条讨论自动改变。
- 先用人工确认的正反样图做成对对照，再用未参与规则调整的图片验证；区分已知错误、正常穿着变形、局部构图及不同款式。不能把AI自己的通过/拒绝当作人工真值，也不能只反复测试参与调参的几个样例。
- 对照记录逐张结论、具体漏判/误杀、人工标注来源、实际调用次数、单图耗时和整批耗时；中断等待与实际运行时间分开统计。小样本结果只能说明该样本上的表现，不足以证明普遍正确率不下降。
- 提速版如新增已知错误放行或已确认正常图误杀，不能据此通过验收或替换正式版。证据不足时保留当前版本，不把调用次数减少直接描述为质量不变。
- 不确定图暂不保存合格目录；仍不足三张时沿用原组最多补生三轮，达到上限暂停。并行和提速不能绕过这些规则。

### 2026-10-29 用户补充的细节标准

- 当前这款原图袖口是平顺外缘，浅蓝三角纹不能被生成为立体波浪、花边或齿瓣。
- 门襟不能增加原款没有的独立边条、衣片层次；注意与贴着折边的正常窄缝线区分。
- 扣子周围也要检查：原图连续平整，结果在每个扣位反复凸出布块或尖角，即使扣数、颜色一致仍不合格。
- 原款长裤需到脚踝附近。裤脚可见时结合小腿、踝骨、脚背、鞋口等判断，不能仅因照片最下方露出的皮肤少就声称及踝；展示但定位证据不清应待复核。
- 裤脚本身未展示时不检查裤长，不把局部构图转成待复核。沿用此前用户确认的可见范围规则。
- 这些案例已证实旧版有漏判，旧验收记录仅代表当时测试结果；新规则须重新独立校准，并复核旧合格输出。

### 用户已明确的要求

- 每一张生成结果都需要与当前商品的原图对比。
- 9 个板块、每个板块 5 张结果都要逐张审核：正常全部成功时，每个商品共审核 45 张，每张各自形成审核结论。
- 不用每组抽查一张来代替整组审核，也不因某一张不合格就自动放弃该组其余图片；其他成功结果仍逐张判断。
- 检查对象是服装的款式与细节，不要求模特、背景、姿势和白底图相同。
- 只审核生成图中实际展示的服装部分。没有入镜或被遮挡的部分不参与该图的一致性判定，不因展示不全而淘汰，也不单独因此转入待复核。
- 错误可能随机出现在任何部位，不能只检查已经出现过的一个错误点。
- 发现与原款不符的图片就舍弃。
- 没有问题的图片才下载并保存到当前商品 ID 文件夹。
- “下载全部”只用于辨认可下载状态，最终留图仍需逐张审核。

### 建议的审核方法

先识别当前原图的实际商品特征，再对生成图可见部分逐项比较，并额外寻找清单之外的新增、缺失或替换细节：

| 检查维度 | 重点 |
| --- | --- |
| 服装组成与版型 | 上下装是否对应、款式轮廓、长短、宽松程度、裤型 |
| 领口与门襟 | 领型、开口结构、包边、蕾丝或装饰 |
| 袖子与下摆 | 袖长、袖口收口、荷叶边、上衣下摆结构 |
| 裤子 | 裤腰、裤脚、收口、长短、额外装饰 |
| 口袋 | 是否存在、数量、位置、形状，不将“所有口袋都禁止”作为规则 |
| 扣子与配件 | 可见扣子的颜色、顺序、形状、数量及其他装饰 |
| 花纹与面料外观 | 图案种类、配色、明显比例、条纹和纹理，允许合理的穿着变形 |
| 颜色 | 主色与细节配色，区分光照变化与明显换色 |

建议对整图和必要的局部细节共同审核，避免只凭缩略图或整图相似度判定。每个判断应说明原图特征、结果图可见特征和差异依据。未展示或被遮挡的部位可以标注为未展示，不参与判定，也不能声称已经核验。实际展示的部位如因模糊等原因无法判断，才按不确定情况处理。

用户已进一步确认：图 3 这类展示不全的图片，只看有展示的部分。例如没有展示裤脚就不检查裤脚；可见服装部分符合原款即可按该图审核范围通过，不要求补齐全身构图。

建议区分三个审核结果：

- 通过：画面中展示的服装部分可判断且未发现不符，进入合格输出目录；展示不全本身不妨碍通过。
- 不通过：发现明确不符，舍弃该图，不进入合格输出目录。
- 待复核：实际展示部分的证据不清、分辨率不足或判断不确定，暂不自动进入合格目录，由人工确认或按后续规则处理；不把未展示部分本身作为待复核理由。

这三个结果已接入 E 板块，并用用户示例及真实生成图做过独立验证。视觉模型包括 Codex 中的模型均可能出错，不能承诺零漏判。用户示例仅用于规则校准，不能当作独立准确率测试集。

## 七、合格图片保存位置

在原白底图所在文件夹下，创建与当前商品 ID 同名的子文件夹，再分成 9 个组文件夹，分别保存对应模特参考组生成并通过审核的图片。例如：

```text
用户指定的白底图文件夹/
├── 商品ID.jpg
└── 商品ID/
    ├── 组01/
    ├── 组02/
    ├── 组03/
    ├── 组04/
    ├── 组05/
    ├── 组06/
    ├── 组07/
    ├── 组08/
    └── 组09/
```

结果图片的具体命名规则尚未指定。临时审核文件和最终合格图片应区分；如需要先取得原尺寸结果图用于分析，可以暂存后审核，只有通过的图片才进入商品 ID 目录。不合格图片不作为交付成果保留。

### 每组不足 3 张时的补生规则（已确认）

- 按每个模特参考组分别统计累计审核通过的图片，不以商品全部 9 组的总数代替组内数量。
- 某组累计合格少于 3 张时，保留已合格的图片，沿用该组原来的 5 张模特参考图和当前商品原图重新生成，不能重新随机换组。
- 新结果仍需逐张审核，通过的图片累计加入原组文件夹；同一张结果不重复计数。
- 初次生成之外，每组最多补生 3 轮。每轮仍按每张参考图生成 1 张、最多 5 张结果执行。
- 达到至少 3 张合格图后不再触发该组补生；不要求仅保留 3 张，初次或最后一轮审核通过的其他结果也保留。
- 用完 3 轮仍不足时暂停该组并提示商品 ID、组号、累计合格数量和补生次数，不无限循环。
- 待复核及技术性生成失败不计入合格数量；技术失败是否按单张补救仍待补充，但不得绕过已确认的组级补生上限。

## 八、交付方案评估

用户要求最终能给其他电脑使用，并明确目前没有另行开通模型 API，希望直接使用 Codex 判断。当前优先探索 Python 配合 Codex 的路线，最终交付形式仍待实际验证后确定。

| 方案 | 运行方式 | 需要验证的事项 |
| --- | --- | --- |
| Python 配合 Codex（当前优先探索） | Python 管理网站操作与文件，通过支持图片输入的 Codex CLI 脚本调用进行审核，读取结果后保存合格图片；CLI 可使用 ChatGPT 账号登录 | 本机 CLI 与登录可用性、账号支持的模型和额度、45 张逐张审核的实际效果与稳定性 |
| Codex 配合 Skill | Skill 保存可复用的规则和脚本，由支持它的宿主与模型执行 | 实际审核效果、账号与运行环境、批量执行方式 |
| 独立 Python 软件配合云端视觉模型 | 本机程序管理网站操作和文件，通过模型接口提交原图及结果图审核 | 图片审核效果、联网可用性、模型调用费用 |
| 独立 Python 软件配合本机视觉模型 | 在本机部署模型进行审核，网站生图仍需联网 | 目标电脑硬件、速度、细节识别能力与实测效果 |

当前已经实测接通“Python 程序 + Codex CLI 审核”，分类、逐图结构化审核及拟通过图的独立复核均成功运行。不把取得 Platform API 密钥作为前提。已完成旧规则下一商品完整九组历史联调，本次质量升级又完成35张旧通过的逐张Sol复核及保存状态升级。另一台电脑和两商品均完整九组尚未验收，不能据此保证所有款式判断准确。

直接在当前 Codex 对话中检查本地图片，可作为前期验证审核规则的方式。后续自动化接入可评估 Codex CLI 的图片输入、非交互执行和结构化输出，使用其支持的 ChatGPT 登录与已有账号额度。目标电脑也需具备相应 Codex 环境和账号访问权限，不随软件复制分发本机账号凭据。

此前讨论的独立 Python 软件调用云端旗舰视觉模型，保留为后续备选方案。模型厂商的旗舰定位不是本项目服装一致性识别的实测排名。当前 Codex 实测使用本机账号默认的 gpt-6.1-sol 与 xhigh 设置，不预设其他账号或其他模型均可用，也未进行供应商间的准确率对比。

建议测试时提供清晰的原图与生成图，在模型支持时保留原始细节，并针对画面中可见的领口、扣子、口袋等区域做局部复核。是否增加复核以及使用何种推理设置，应以错误图片被放行和合格图片被误杀的实测结果决定。Codex 或独立软件的包装形式本身不决定识别准确率，实际模型、图片处理、审核指令、上下文和参数均会影响结果。

OpenAI 官方资料确认 API 可输入多张图片进行视觉分析，也说明模型可能出现描述、定位和计数错误。Skill 是复用指令与资源的机制，不能仅靠把程序封装成 Skill 就保证图片审核准确。
